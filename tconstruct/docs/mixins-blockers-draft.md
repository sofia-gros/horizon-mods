## Destructured function parameter

**Target:** `horizon_client_render::mesher::Mesher<'_>::face`. The host's parameter list includes `(id, state): (u32, &Info)`. A single `HEAD` injection using `storage-mesh-face.rs` and the bindings from `horizon-mixin.toml` produces `E_INVALID_BINDING: destructured function parameters are unsupported` on the earlier `40e044da777dfb56fd9df2ff0fc2b0a3abba4578` host. The target has the same destructured parameter in `5afa1de5f750b4b89ca23347b1d3aba296c278b0`. The one-injection plan was rerun on `3a264943c7a3a3ed02e6ee608443f558d98f208f` with Mixins `ddd9700b21997c95d95ac6ee5ecafe3830cf622a` and returned the same diagnostic.

**Required behavior:** each affected face needs the original state, absolute block position, face, output mesh and sprite/lighting context. The `quad` and `quad_as` boundaries lack that context. A previous `AFTER_CALL` probe at `mesh_reusing` / `self.face` on the earlier revision failed with `E_UNSUPPORTED_CONTROL_FLOW` in the enclosing closure.

**Possible upstream enhancement:** support bindings for identifiers of a proven irrefutable tuple pattern without changing the original parameter evaluation or borrow/lifetime rules. A suitable upstream test would inject into a minimal `fn face((id, state): (u32, &Info))`, check both bound values and original behavior, and cover shadowing and mutable/borrowed patterns. Unsupported patterns should continue to fail closed.

## Wear calculation and macro identity

**Target:** `horizon_client::game::enchant_effects::Game<'_>::durability_loss`. A single `RETURN` injection from `dense-durability-loss` / `source-dense-wear.rs` returns `E_UNSUPPORTED_MACRO: macro identity is ambiguous; use an unshadowed absolute standard path` on `40e044da777dfb56fd9df2ff0fc2b0a3abba4578`. The function invokes `world_stations!` and `world_items!`. On `5afa1de5f750b4b89ca23347b1d3aba296c278b0`, this target was not rerun; the earlier revision diff does not modify its source file. A one-injection plan with a no-op `u32` helper was rerun on `3a264943c7a3a3ed02e6ee608443f558d98f208f` with Mixins `ddd9700b21997c95d95ac6ee5ecafe3830cf622a` and returned the same diagnostic.

**Required behavior:** adjust the returned wear once before the caller's native damage event and durability trigger, including direct creature and dispenser calls. `RETURN` at `wear` plans successfully but executes after those events and omits direct callers. On `5afa1de5f750b4b89ca23347b1d3aba296c278b0`, `MODIFY_EXPRESSION_VALUE` on `self.durability_loss(stack, amount)` inside `wear` plans successfully and would occur at the needed point. Separate one-injection probes for `self.durability_loss(&stack, amount)` in `wear_sun_protection` and `hurt_and_break` both return `E_UNSUPPORTED_CONTROL_FLOW` for their enclosing closure. These plans alone do not type-check captures or establish that every direct path can be safely covered.

**Possible upstream enhancement:** resolve an unambiguously indexed local macro identity for a `RETURN` target while continuing to reject unresolved, shadowed or opaque control-flow macro identities. An upstream fixture should cover safe resolution, shadowing rejection, exactly-once side effects and generated Rust type checking. Alternatively, carefully scoped expression modification in a closure-containing target could be supported if its lexical and control-flow safety is proven. Neither proposal recommends disabling the existing checks.

## Support module source headers

Before submitting or combining Mixins support modules, run `python3 tools/check_mixin_module_headers.py` from the repository root. It reads every checked-in TConstruct and PlutoLib mixin manifest, resolves each `[[module]].source` relative to that manifest, and reports missing sources, unreadable manifests, inner documentation (`//!` or `/*!`), inner attributes (`#![...]`) and shebang lines. Use repeatable `--manifest PATH` to inspect a particular manifest. A module copied into a host source file must use regular comments such as `//` rather than file-level documentation or attributes. The scan is conservative and a reported marker inside a string should be inspected manually.

The check is a static preflight, not a Mixins plan/apply, Rust type check, package validation, build or gameplay test. It only describes the checked-out sources; inspecting fixed PRs requires each exact head. Never change an already-fixed verification head merely to make this check pass; prepare a separately identified follow-up.

The 2026-11-02 open-PR snapshot covered 220 exact heads, 4,825 manifests and 42,500 module references under TConstruct and PlutoLib, including examples and experiments. Seventeen distinct source paths were flagged in 66 historical heads; the current follow-up based on #317 has no flagged sources. The complete head-to-path mapping and errors are recorded in [the audit evidence](evidence/module-header-audit-20261102.json). This is a point-in-time source scan, not evidence that the affected heads fail for any other reason or that clean heads pass Mixins apply.
