# Glowing ability (in progress)

Glowing's source recipe uses glowstone, a daylight detector and shroomlight, consumes one ability slot and permits one level. It applies to the source interactable-or-boots durability tag. Source: TConstruct `f4e77d43f39ba1047bf93ae816b7e1beaab514c2`, `ModifierRecipeProvider` and `ModifierProvider`.

The source light is `tconstruct:glow`, emits level 14, has no collision or drops, and attaches to a full solid face. A placement uses the clicked face first, then tries other supporting faces; liquid and existing glow are rejected. A surviving glow is removed when its support disappears. A successful direct placement costs five durability with cause `tconstruct:glowing`; broken tools do not place it. The source also has boot walking in low block light and projectile hit placement, with its own launch/hit wear rules. The original glow texture, model and directional blockstate are included from that pinned revision. A six-direction light-level-14 block is declared and resource preparation assigns empty collision. The support-face lookup, an update queue, source selection outline and direct right-click path are connected. Recipe and ability-slot handling use the original recipe, including Crystal reapplication. At runtime `a5659de5040e8406b310fb7120af532d4da88e7c`, direct use placed a source light and consumed five durability in an integrated-server fixture. Boots walking is connected to the existing local/LAN location-change path with the source radius and light conditions. Left-click is connected for the source interaction tags and toggles, including guest actions. At runtime `5905ed71bc4ccb7ac70635cce7b98ffb1edbd1ab`, a dedicated-server dark-corridor fixture with supplied Glowing boots placed outside the spawn-protected square for an ordinary player and inside it for an operator; both lost five boot durability. A held left click incorrectly placed two lights and consumed ten durability. At runtime `486427cb7623fbfcc2c0763257405c30c0a8c10d`, the client tag-resolution change was formally transformed and built; holding left click placed one light, consumed five durability, and preserved the clicked block. Live Longbow and Crossbow arrows now charge the original five durability at primary launch and attempt placement on impact; each placement uses the actual firing guest’s protection policy. A successful block placement removes the arrow; rejected placement leaves ordinary collision handling in control. This restored path awaits formal build and game validation. Saved-arrow reload, rockets, fishing hooks and player-hit paths remain unimplemented.

The shared placement selector implements the preferred face, source fallback direction order, support checks and rejection conditions. Placement uses the acting guest’s host-resolved spawn-protection policy for each candidate; missing actor context fails closed on a dedicated server. Six lightweight tests cover selection, invalid destinations, walking geometry, source interaction toggles and the protection boundary; the tests do not substitute for game verification.

The durability hook has a scoped modifier-cause path, so Glowing actions can pass their actual cause through Tanned, Overslime, Unbreakable, Dense and Reinforced. The existing ordinary-wear callers still pass no cause. Limited Mixins plan and lightweight formula tests passed. The two runtime SHAs above passed full transformation and target builds; the later runtime was also formally transformed and built. The latest runtime repeated the dedicated-server direct-use and walking protection checks described above. Direct use passes the Glowing cause on a successful placement. The remaining source actions are required before this ability can be considered complete.

The pinned Mixins plan rejects a projectile struct extension (`E_STATE`: all fields are public). Both a return hook on `horizon_client::entity_nbt::arrow_from_nbt` and an operation hook at its `Game::spawn_loaded_entities` call report `E_UNSUPPORTED_CONTROL_FLOW` because of unsupported `?` or closure contexts. Consequently Glowing on an in-flight arrow is not retained across save/reload; no ammunition component or vanilla item data is repurposed.

Remote clients predict left-click eligibility from locally available built-in and source-pack item tags. The host still validates its own authoritative tags and spawn protection. The host’s enabled world datapacks are private in this API, so server-only tag changes may disagree with the client prediction and are not verified. Supplied Glowing tools and boots and a constructed dark corridor were used in these checks; recipe acquisition, Crystal, save/reload, projectile behavior and Windows were not tested in this run.
