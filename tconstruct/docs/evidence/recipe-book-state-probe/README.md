# Remote recipe-book state feasibility

2026-11-02. Against archived Horizon `02c8607ee8ebd216f2f535c1eb7b62b572830df2` and Mixins `ddd9700b21997c95d95ac6ee5ecafe3830cf622a`, this isolated Mixins bundle tried adding per-instance maps to the remote `RecipeUi` and synchronized `Dynamic` registry; it is a feasibility experiment, not a product patch. Both types use derived Default without explicit own struct literals. An empty constructor declaration is rejected as `E_STATE: state requires explicit constructors with positive require counts`. `Dynamic` also exposes public fields and has struct literals outside its crate; Mixins' state contract does not permit silently extending such a publicly constructible type.

A correct generic packet-based book needs to retain all received entries by server display ID, process replace/remove and reconnect/reload, decode category and all supported display variants, resolve requirements and server item tags, and use the server ID for place/ghost. In this revision `Dynamic::add_tags` stores only dialog tags; received item tags are not available there for server-authoritative filtering. Local content tags cannot safely stand in for server data packs. A single global map or icon-only patch cannot establish per-connection lifecycle and may enable wrong placement. A supported host/native API carrying per-connection recipe displays and item tags, or a Mixins extension capable of safe state on default-constructed types plus packet/tag lifecycle hooks, is needed before the full PlutoLib integration can be safely implemented. No Pattern rewards have been shipped from this experiment.

A second isolated probe supplied `horizon_client::game::recipe_book::<RecipeUi as Default>::default` as an explicit constructor. The fixed Mixins apply returned `E_TARGET_NOT_FOUND`: the method is derived and has no source function body to select (`default-apply.log`). This confirms the precise state-injection limitation; it does not prove that a host-side change or a future Mixins extension is impossible.
