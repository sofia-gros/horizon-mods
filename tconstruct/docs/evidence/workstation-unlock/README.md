# Workstation recipe unlock blocker

2026-11-02, local fixture using prior final client `955f2d745b901f90a8a1858303d809c975f17c65e584f67cf08d100fe74a39b0`, tree `dbcfba54881049687da34d8c31462cede8b1802f`, PR 199 recipe/tag bytes and experimental source-derived advancement JSON. Pinned source `f4e77d43f39ba1047bf93ae816b7e1beaab514c2` defines Pattern inventory_changed advancements rewarding `tconstruct:tables/part_builder` and `tconstruct:tables/tinker_station`. Their runtime recipe IDs are adapted to `tconstruct:part_builder` and `tconstruct:tinker_station` in this fixture.

Giving a Pattern completed both experimental advancements, but the actual recipe book showed neither workstation. The tested build source at `02c8607ee8ebd216f2f535c1eb7b62b572830df2` reads the base `data/minecraft/recipe` tree and also merges recipe files from the world datapack overlay, including non-Minecraft IDs. It does not enumerate the base content-mod `data/<namespace>/recipe` files in this path. Awarding a recipe still filters through that index. The resource's command-registries learnable list also lacks the two IDs, but the code path above is the direct explanation. This is a host recipe-book dependency; it is not proof of a PR 199 crafting regression.

Do not ship the experimental advancement data alone: it can save the advancement as complete while its absent recipe reward is filtered out, so correcting the index later would need a recovery path for already completed players. A complete fix must load namespaced mod recipes, preserve display identifiers and local/LAN sync, handle already-completed progress if applicable, and then verify both fresh and existing players, recipe book and save/reload. The data remains uncommitted in `/workspace/scratch/workstation-unlocks`; it is not a proposed finished fix.
