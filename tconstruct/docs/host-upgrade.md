# Horizon host update (draft)

This work targets official Horizon `5afa1de5f750b4b89ca23347b1d3aba296c278b0` and Horizon Mixins `ddd9700b21997c95d95ac6ee5ecafe3830cf622a`. It adapts the existing TConstruct integrations before the slime-island draft is based on it. This is a compatibility work in progress, not a validated build or a claim that slime islands generate.

The new host supports content block `state_properties` and `default_state`, which may represent the source vine stages. Its world fluid kind still contains only empty, water and lava families; the original slime world fluids remain unresolved. Do not enable incomplete island generation or replace slime fluid with water.

Plan, type checking and representative regression results will be recorded here once run. Existing crafting, GUI, save/reload, LAN, equipment and casting paths all need revalidation after adaptation.

The first full plan stopped at `E_BRIDGE_TARGET` for the old `horizon_client::chunk_map::ChunkMap`: the host moved that struct and `DataPack` into `horizon-client-render`. Their targets have been moved in this draft. The next full plan stopped at `E_MODULE` for the removed `crates/horizon-client/src/logging.rs`; resource modules and the preparation entry have been moved provisionally. A limited plan for those moved resources and render targets, excluding the three face injections, accepted 4 injections, 8 modules, 2 bridges and 1 representative state.

The current `horizon_client_render::mesher::Mesher<'_>::face` has a destructured `(id, state)` argument. Mixins reports `E_INVALID_BINDING: destructured function parameters are unsupported` for the existing face hooks (storage, connected glass, and chest tint). A limited `AFTER_CALL` probe on `Mesher::mesh_reusing` / `self.face` instead reports `E_UNSUPPORTED_CONTROL_FLOW` because the enclosing function contains a closure. Neither result proves every alternative is impossible; those visual paths remain unadapted and must not be dropped or declared working. The non-`cfg` `horizon_client::entry::main` was accepted by the limited plan; the candidate `main_with` was rejected with `E_UNSUPPORTED_CFG`. Plan acceptance does not establish Rust type correctness or runtime behavior.

The first limited type check included only one injected state and correctly failed on the omitted state accessors; it also exposed the old atlas initializer missing new host fields. An all-85-state limited transform removed those state errors, then type checking reached the resource module: placing it in `horizon-client-lib` could not see the existing TConstruct modules that remain in `horizon-client`. The draft now places the four resource modules alongside those modules instead. This placement still needs a type check with their real dependencies. The new atlas candidate injects source sprite registration through the host's existing `Sprites::insert` path; its individual limited plan passes, but its Rust types and rendered results remain unverified.

The subsequent transform with the real module dependencies stopped at `E_MODULE_CONFLICT` for `tconstruct_block_shapes`: the new `crates/horizon-client/src/lib.rs` contains `pub use horizon_client_lib::*`, and Mixins refuses to add the support module alongside an unresolved glob import. Consequently this attempt did not reach Rust type checking. A safe relocation or official Mixins handling of that import is still needed; neither this resource path nor the host update is validated.

Grouped limited plans also reached `E_UNSUPPORTED_MACRO` at the durability, knockback and inventory-click hooks, where Mixins reports ambiguous macro identity in the new host functions. The former `effect_attack_bonus` target no longer exists; the new attack attribute and enchantment pipeline requires a semantic adaptation rather than a simple rename. Machine interaction now uses the host's `InteractionResult` return type; that change has passed the relevant plan stage but not a complete type check. LAN and save targets have been moved to their new client-library owners and likewise remain unvalidated.

The newer `Game::wear` delegates to `durability_loss`, but creature and dispenser paths also call `durability_loss` directly. Moving the modifier hook to `wear` alone would omit those callers, so it is not an equivalent blanket replacement.

After these paths are adapted and the complete plan and targeted checks pass, the intended single regression build and game pass covers crafting and station transactions, equipment and attacks, atlas and connected-block rendering, casting, persistence, and local and LAN interactions. It must use the fixed host and Mixins commits above. Windows and dedicated-server behavior need their own evidence; neither is established by a Linux build. Island generation remains disabled until its original materials, world fluids and feature placement are connected and validated.

Attack-path inspection on Horizon `5afa1de5f750b4b89ca23347b1d3aba296c278b0`:

| Path | Authoritative computation |
| --- | --- |
| Single player / LAN host attacking a mob | `Game::attack` → `attack_mob` → `melee_damage` → `attack_damage` |
| LAN guest attacking a mob | Host `guest_attack` swaps in the guest with `as_guest`, then calls `attack_mob` and the same computation |
| Host or guest PvP | `pvp_strike` uses `melee_damage` on the attacking player; the host applies the strike |
| Remote client prediction | `remote_player_attack` uses `own_attribute` for attacker slowdown; it is not the server's damage computation |

The old `effect_attack_bonus` hook is provisionally moved to `attack_damage`. It evaluates the TConstruct material delta as an additive modifier on a cloned player attribute map, retaining host-side strength, weakness and attribute operation ordering without modifying the live map. A single-injection limited plan succeeds; this is not a type check or proof of once-only damage, equipment synchronization, prediction, or TConstruct damage and durability behavior. These require the later combined build and game checks.

On `40e044da777dfb56fd9df2ff0fc2b0a3abba4578`, the one-injection `Mesher::face` plan returns `E_INVALID_BINDING` for its destructured `(id, state)` parameter. Its lower-level `quad` lacks the source block, position and material context required by the storage, connected-texture and chest hooks. Candidate minimal upstream improvements are safe bindings for destructured parameters and unambiguous resolution of local macro identities in injection targets; no diagnostic is disabled. These diagnostics were obtained on `40e044da`, not a completed full plan on the final coordinated revision.

The Creative integration fixtures cover vanilla search metadata, ordered TConstruct groups and a previously generated material-and-stat-bearing stack. This does not execute native startup or validate the current build.

Both `tools/resources.py` and `tools/package_hmod.py` generate groups with `build_variants` and `add_block_items`. Native startup enriches those groups before shared registration. Manual preparation first creates an intermediate overlay with the Python helper; its final `creative` step removes the intermediate TConstruct tabs, enriches them, and registers them through the same Rust API. Focused tests compile the extracted adapter and fixed host parser, preserving final components, existing search metadata and permission indexes, and rejecting repeat registration. They do not execute the entire preparation pipeline. Native packaging and installation of the separate PlutoLib bundle remain unresolved; do not treat the current artifact as standalone. `tools/stage.py` requires `pluto_native_creative` and rejects the legacy paging adapter.

A further call-result probe is recorded in [the unposted Mixins investigation](mixins-blockers-draft.md): `wear` can be intercepted before its native event with `MODIFY_EXPRESSION_VALUE`, but separate creature and dispenser caller probes are rejected due to closure-containing target functions. The draft is not an upstream submission.

Native startup is injected at `load_resources` HEAD. Both synchronous and loading-screen startup call `mods::content_root` before `load_resources`; the TConstruct `.hmod` must not declare the same Creative tabs for Horizon's content merge to register first. Resource-pack reload and the complete staged game still need verification. The current PlutoLib bundle's crate declaration adds `pluto-creative-api` to `horizon-client` and has no injections, so stage that bundle exactly once beside TConstruct. The official `horizon-native.json` has no general dependency field and rejects unknown fields. Horizon also documents trait `[api]` package dependencies, but neither of these current Mixins-only bundles supplies that trait API arrangement; it cannot be asserted to enforce this dependency. The existing TConstruct `.hnmod` packager includes only its own bundle, so it cannot yet deliver the shared bundle automatically.

For distribution, the intended supported flow is two separately packaged and enabled `.hnmod` files, each with its own matching manifest ID and `mixins/<id>/horizon-mixin.toml`. `launcher/src/native_mods.rs::installed_mods` validates and extracts enabled files by ID, and `stage_mixins` sends their bundles together to Mixins. PlutoLib's `[[crate]]` adds `pluto-creative-api` once to `horizon-client`; it has no initialization injection. TConstruct's content `.hmod` is also required, and must not declare duplicate Creative tabs. Official bundle validation permits sources only below the single manifest ID and refuses unknown native manifest fields; it is not a supported nested-two-bundle dependency mechanism. The existing TConstruct artifact cannot provide the separate PlutoLib bundle, and packaging both independently has not been generated or launcher-tested. The PlutoLib side needs its own matching native manifest and distribution artifact, plus clear installation guidance and coordinated versions; the old paging adapter must remain separate.
