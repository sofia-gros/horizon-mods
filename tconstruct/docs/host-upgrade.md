# Horizon host update (draft)

This work targets official Horizon `e12185820a6bc85dd5ed04adc7b8b7a4bdc16102` and Horizon Mixins `ddd9700b21997c95d95ac6ee5ecafe3830cf622a`. It adapts the existing TConstruct integrations before the slime-island draft is based on it. This is a compatibility work in progress, not a validated build or a claim that slime islands generate.

The new host supports content block `state_properties` and `default_state`, which may represent the source vine stages. Its world fluid kind still contains only empty, water and lava families; the original slime world fluids remain unresolved. Do not enable incomplete island generation or replace slime fluid with water.

Plan, type checking and representative regression results will be recorded here once run. Existing crafting, GUI, save/reload, LAN, equipment and casting paths all need revalidation after adaptation.

The first full plan stopped at `E_BRIDGE_TARGET` for the old `horizon_client::chunk_map::ChunkMap`: the host moved that struct and `DataPack` into `horizon-client-render`. Their targets have been moved in this draft. The next full plan stopped at `E_MODULE` for the removed `crates/horizon-client/src/logging.rs`; resource modules and the preparation entry have been moved provisionally. A limited plan for those moved resources and render targets, excluding the three face injections, accepted 4 injections, 8 modules, 2 bridges and 1 representative state.

The current `horizon_client_render::mesher::Mesher<'_>::face` has a destructured `(id, state)` argument. Mixins reports `E_INVALID_BINDING: destructured function parameters are unsupported` for the existing face hooks (storage, connected glass, and chest tint). A limited `AFTER_CALL` probe on `Mesher::mesh_reusing` / `self.face` instead reports `E_UNSUPPORTED_CONTROL_FLOW` because the enclosing function contains a closure. Neither result proves every alternative is impossible; those visual paths remain unadapted and must not be dropped or declared working. The non-`cfg` `horizon_client::entry::main` was accepted by the limited plan; the candidate `main_with` was rejected with `E_UNSUPPORTED_CFG`. Plan acceptance does not establish Rust type correctness or runtime behavior.

The first limited type check included only one injected state and correctly failed on the omitted state accessors; it also exposed the old atlas initializer missing new host fields. An all-85-state limited transform removed those state errors, then type checking reached the resource module: placing it in `horizon-client-lib` could not see the existing TConstruct modules that remain in `horizon-client`. The draft now places the four resource modules alongside those modules instead. This placement still needs a type check with their real dependencies. The new atlas candidate injects source sprite registration through the host's existing `Sprites::insert` path; its individual limited plan passes, but its Rust types and rendered results remain unverified.
