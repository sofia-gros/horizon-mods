# Budding slime crystal piston candidate

At TConstruct `f4e77d43f39ba1047bf93ae816b7e1beaab514c2`, `BuddingCrystalBlock.getPistonPushReaction` returns `DESTROY` for Earth, Sky, Ender and Ichor crystals, and source loot for budding crystals is empty. On horizon-mods `2f022395` the four use the `minecraft:amethyst_block` template for their existing custom random tick. In a previously prepared local host snapshot, their gameplay rows were `PUSH_PULL`, whereas vanilla budding amethyst was `POPPED`. Consequently the port could move or sticky-pull a source budding crystal instead of destroying it.

This candidate leaves the block template, source crystal growth code, random tick and loot alone. It validates the four expected single states and their existing reactions, then changes only those prepared gameplay rows to `POPPED` (Horizon host's spelling for its destroyable piston reaction). The preparation cache key changes from v6 to v7 so an old derived cache is not reused. Absent, duplicate, malformed or misaligned target inputs fail before this function writes any row. A target row whose registry ID does not match its array index, or whose reaction is an externally overridden value, leaves all four rows unchanged and emits a warning. It does not change normal slime crystal blocks, buds, vanilla amethyst or modded states.

Static source comparison also checked all six Cobalt small/large ore and Earth/Sky/Ender/Ichor geode configured features after translating source provider and state syntax to Horizon's representation: their content values matched. All four geode placement resources and small Cobalt placement matched source exactly; large Cobalt additionally spells out the host's default zero plateau. Cobalt's pickaxe and iron-tier tags agree with pinned source. These checks do not establish world distribution or actual harvest.

The production correction passed three Rust tests, including application to a real previously prepared local facts/gameplay snapshot where exactly the four target rows changed, seven scoped Python wiring, Cobalt/geode and prior piston tests, and the two existing isolated geode-growth helper tests. The snapshot and module test are not a candidate integrated build. Source growth behavior, natural placement, piston extension/retraction, loot, saved chunks, gameplay and LAN remain unverified on the target build.

The repository's condition-snapshot harness also passed with the new module included: 39 passed, 1 ignored. It is a standalone harness, not a transformation or whole-host compilation.

## Reproducing the snapshot check

`tests/fixtures/budding-piston-prepared-snapshot.json` contains the six unmodified selected `facts.json` and `gameplay-facts.json` rows from the prior local prepared resource tree: four TConstruct budding crystals and vanilla amethyst/budding amethyst controls. Arrays are compacted in original order; each gameplay row retains its original `id`. The pre-correction full input files had SHA-256 `9ed875af678ec5d401fa7d9ee22b934e06017a359f39bf28337b69b453fb37b4` (facts) and `80cf268cc9b49a51871a134437aa3ebe0f992549790a700c53f8bb557c6a19db` (gameplay facts). The previously built preparer binary had SHA-256 `adbf48ad88035959ab2d7b8442bc69ec8412f98024514ff0042ae7ace3423ae5`; its exact source revision was not established, so this is evidence about that local snapshot, not the formal target host.

From the repository root, `cargo test --manifest-path tconstruct/tests/condition-snapshot/Cargo.toml extracted_prepared_snapshot_changes_only_four_push_fields` expands the committed compact fixture back to its original registry indexes and runs the production correction and verifies exactly four changes, only to `push`, with both vanilla control rows unchanged. The complete harness now reports 40 passed and one ignored. No external source checkout or host resource root is needed for that fixture test. To extract the same selected rows from a compatible independently prepared resource tree, run `python3 tconstruct/tests/extract_budding_piston_snapshot.py RESOURCE_ROOT > selected.json` and compare the JSON with the fixture. Different host builds, installed content or registry ordering may legitimately produce different rows. Upstream `BuddingCrystalBlock.java` at `f4e77d43` is the separate source evidence for `DESTROY`; it is not embedded in the snapshot and `/tmp/tconstruct-upstream` is not required to run this check. Neither fixture test runs a piston, proves runtime behavior, nor substitutes for a candidate integrated build or LAN validation.

The snapshot test lives in the standalone harness rather than the production Mixins module. The module is embedded into host Rust sources during transformation, so a repository-relative include inside it would resolve against the host source tree during host tests. This placement avoids that path dependency; it does not itself prove an integrated host test.
