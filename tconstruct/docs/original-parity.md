# Original parity tracking

The specification is the complete Tinkers' Construct 1.20.1 tree at
`f4e77d43f39ba1047bf93ae816b7e1beaab514c2`, including behavior, appearance,
content, data, input, rendering, audio, persistence and multiplayer. An internal
implementation may differ where its observable behavior is equivalent; the
prototype's user-visible differences below are gaps, not alternative targets.

[upstream-tree.txt.gz](upstream-tree.txt.gz) indexes all tracked upstream
paths, regenerated by `python3 tools/upstream_inventory.py /path/to/clone`.
The file inventory is an audit aid, **not** an assertion that each file has
been analyzed or mapped to a feature. The coverage matrix is incomplete until
registrations, data-driven combinations, lifecycle paths and their tests are
mapped. [Feature matrix](feature-matrix.md) and [roadmap](roadmap.md) identify
known gaps; missing entries must not be interpreted as implemented.

[upstream-recipes.json.gz](upstream-recipes.json.gz) contains the original
JSON and source path for all 338 generated material recipes, 28 Part Builder
recipes and 23 station layouts; regenerate it with
`python3 tools/reference_catalog.py /path/to/clone`. Every catalog entry is
currently marked `unreviewed`: the prototype coverage in the table below is
partial and does not establish parity for an entire recipe. These are file counts,
not verified counts of active features; conditions, aliases and runtime
registrations still have to be audited. The current source-recipe path covers only a subset of those definitions. The material directory includes 217 material-input
recipes, 73 fluid material recipes and 48 material-melting recipes; the part
builder directory contains 24 material-part and four item-part recipes. This
counts source `type` fields, not enabled recipes. Conditions, leftovers and
nontrivial ingredient forms require implementation, not conversion to fixed
item matches.

## Source recipe files in the resource overlay

`content/data/tconstruct/recipes/` carries all 217 pinned material-input
recipes and 28 Part Builder recipes as individual JSON files, retaining their
source paths and IDs. `tools/export_part_builder_reference.py` regenerates the
same semantic data from the pinned reference catalog and refuses to overwrite a
different existing file; `tests/test_source_recipes.py` compares every file
with that catalog. The official content overlay was checked to retain all 245
files. These files are source data only: the game does not yet load them for
Part Builder transactions. A per-world raw recipe snapshot now follows the
Horizon enabled-pack order and refreshes on `/reload` and pack changes. An
independent probe tested pack priority, disabling, reload, and two worlds in
both game modes; it does not validate recipe decoding or gameplay. Live tag
and configuration resolution, recipe conditions and transactions remain open.
Raw 1.20.1 `tags/items` files are now retained in pack order in a separate
world snapshot. The unconnected tag helper handles ordered `replace`, Forge
`remove`, nested, required and optional entries; cyclic references are
currently rejected and are not claimed to match the original dependency
sorter. The 427 original generated item-tag files are retained in a separate mod pack
with their bytes checked against `docs/upstream-tags.sha256`; the preparation
step also puts all 3,067 pinned generated TConstruct recipes in that pack
from `content/reference/tconstruct-recipes.zip` (SHA-256
`d84f5da24c464af5d6b158ddf324c0de0f2b27a5cdeb8737cace6d6ab4699951`),
so disabling the vanilla pack does not disable mod data. The setup can extract Minecraft 1.20.1 item tags from the user-supplied
client jar after verifying Mojang’s published SHA-1, and Forge 47.4.0 item
tags and recipes from its official universal jar after verifying SHA-256
`2b0e97b22fd4d043dbbcc8e0a44ef0d58915689ed9224e4cd28d5c4976a16bcc`.
The Minecraft 1.20.1 recipes are extracted from the same verified jar. Horizon
26.3 base recipes may also enter the snapshot; exact source precedence and
isolation, the world registry and resolved tags are not yet connected to Part
Builder. Both game modes were probed for raw tag-pack order, 3,067
TConstruct recipe IDs, Minecraft recipe bytes, a Forge override, reload,
disabling and world separation, not for crafting with resolved tags.

`source_material_lookup` is an unconnected prototype that applies the source
order, ingredient and condition helpers to a supplied complete context, and
returns the original material value, needed quantity and leftover descriptor.
Tests using the 217 pinned material definitions cover flint, oak logs and
oak versus warped planks in a controlled tag context, including three
remaining oak planks for a one-unit part cost and the source wood variant ID. Unknown configuration and incomplete input are rejected. This is
not world-registry, GUI or transaction coverage; tool-part material recycling
and arbitrary custom recipes also remain incomplete.

The original source pack also retains 104 material definitions, 99 stat
files, 99 trait files and 18 material-tag files, in
`content/reference/tconstruct-materials.zip` (SHA-256
`5076dc235c89022d26f71e8c125ba073977e9c540adedb628c897fd7c657e6c7`). The
world snapshot retains every pack layer. Source-based helper tests cover
material definition defaults, redirects, conditions, the `forge:and` condition,
stats field merging and removal, and raw trait list replacement. Material
registry construction, tag resolution, stat deserialization, trait fallback,
modifier behavior and the Part Builder are not connected. The current raw
helpers fail closed for unsupported values and do not yet match the original
loader's full error behavior.

`source_part_choices` is an unconnected prototype of the original selection
list for `PartRecipe` and `ItemPartRecipe`: given complete tag, material and
output-support contexts, it filters partial matches, orders recipe IDs by the
source ResourceLocation comparator, keeps the first recipe per pattern, then
sorts buttons by cost and pattern. Tests parse the 28 pinned recipes and cover
empty material, uncraftable allowances, item-recipe variants and duplicates.
An independent fixture tested a controlled server-side context in both game
modes: all 28 empty-material choices, three wood-supported choices, and
world-pack cost overrides, ordering, reload, disabling and world isolation.
The 37 `tconstruct:part_builder_recycling` and 15
`tconstruct:part_builder_tool_recycling` recipes are parsed and combined with
ordinary candidates. The first type is connected to GUI transactions for
supported damageable items and resolved output alternatives; modifiable-tool
recycling and incomplete contexts remain unsupported. `PartBuilderRecycle`
selects uniformly from alternatives using the shared Rust RNG. Map
iteration and other original users of the RNG are not yet reproduced, so a
particular seeded sequence is not claimed to match the original.
The source recycling recipes use `TinkerFluids.venomBottle`: it has a
16-item stack limit, glass-bottle crafting remainder, venom fluid content and
food effects. It is registered and command-supplied tests verify its glass-bottle remainder; normal acquisition and general fluid capability remain incomplete. The smeltery container-transfer path now supports emptying a Venom Bottle into 250 mB of venom and returning a glass bottle; a supplied bottle returned a glass bottle in a Linux game, and blocked output preserved both inputs across reload. Saved block-entity data confirmed 250 mB transferred and no transfer on insufficient capacity. LAN and Windows remain unverified.
`PartBuilderBlockEntity.onCraft` gives the recipe leftover before shrinking
inputs; its `shrinkSlot` also returns each input item's crafting remainder
(multiplied by consumed count). Reproducing both paths is required for venom
bottles and must not be inferred from the preview alone.

Tool recycling without a recipe-level `parts` override depends on the
world's `ToolDefinitionLoader` and its `ToolPartsHook`. The pinned source pack
now contains all 45 generated tool definition JSON files, preserved byte for
byte; the world snapshot keeps their ordered pack layers. The original loader
selects the highest priority file and only applies it to registered tool
definitions. An independent fixture tested the original pickaxe bytes and
world-pack priority, disable, reload and two-world isolation in both game
modes. Full module decoding, registered tool validation and gameplay
integration remain unfinished. A test-only
ToolPartsHook extractor accepts a separately validated module/item context,
and the recycling pattern helper accepts separately validated material stats.
A fixture using a controlled module context and the current item registry
checked source pickaxe parts and a shield-core datapack override, including
reload and two worlds, in both game modes. Neither helper is connected to the
real module registry or player transactions.

The world snapshot also attempts item-tag resolution against the actual
Horizon item registry. Missing required references omit their tag, while
cycles fail closed because Forge's dependency sorter is not yet ported. In
one locally prepared fixture resource set, 274 of 616 fixed source item tags resolve;
342 do not, including tags referencing unregistered TConstruct items. This is
not an original-equivalent item registry. If `config/tconstruct-common.toml`
is absent, the source condition defaults are captured per world; if it exists
or cannot be inspected, configuration is explicitly unavailable. Forge TOML
parsing and user overrides remain unimplemented. A server-side fixture in both
game modes verified actual oak-log and Pattern tags through pack replacement,
disabling and reload; flint and oak-log material lookup with real item tags
and default configuration; and rejection of a present common config file.
Other registries remain incomplete and these contexts are not used for player
crafting yet.

`source_part_plan` prototypes the source's single-craft arithmetic for the
two supported recipe serializers: ingredient quantity, default or reusable
pattern consumption, extra part count and the material leftover descriptor.
The caller must still revalidate the selected pattern and conditions. Item
container returns, tag-output resolution, inventory capacity, crafting events,
sounds and atomic commit are not implemented by this plan; it is not used by
player gameplay.

All 62 pinned source pattern textures are copied into the client GUI atlas;
an independent fixture checked their registration when opening the Part Builder
in both game modes. The current screen does not yet draw these patterns. The
single-craft plan was also checked with real world tags and default configuration,
but with controlled material support and craftability; it does not mutate slots.

`source_supported_original_parts` maps the pinned `ToolPartItem` registrations
to stat IDs and handles the repair-kit's separate repairable-stat condition.
Fake ingots and storage blocks are not covered. Its inputs must already be validated by the source stat registry;
raw JSON keys alone are insufficient. This mapping has a unit test but is not
connected to the registry or gameplay, and does not cover other mods' items.

Source material definitions and material tags now have per-world snapshots
that preserve pack layers and reject unsupported context. A missing
fluid registry is treated as unknown, rather than as an empty registry: the
source treated-wood definition can depend on `forge:creosote`. Fake ingot and
storage block checks have a separate source arithmetic prototype, but need the
actual material tags and visible base-material recipe cache before use. None of
these snapshots is connected to the player crafting transaction. In both game
modes, a fixture observed the original treated-wood condition change as the
world's creosote tag was overridden, disabled and reloaded, while a second
world remained independent. The snapshot reflects Horizon's current incomplete
item and fluid registries, and unsupported source data fail the snapshot.

The stat snapshot follows `MaterialStatsManager`'s layer merge and the
`HeadMaterialStats`, `HandleMaterialStats`, `LimbMaterialStats`,
`GripMaterialStats`, `PlatingMaterialStats`, `RepairStats`, `SkullStats`,
`SlimeStats` and `StatlessMaterialStats` loaders. It validates the original
built-in stat types and merges layers
before deriving each material's available parts. All 99 pinned stat files have
targeted tests. An independent fixture uses the world snapshots and confirms in
both game modes that removing and restoring flint's head stat changes the
recipe-derived pick-head choice. This is not connected to the player GUI or
transactions. Unknown added stat types, added tier IDs and
numeric encodings outside the implemented range explicitly fail the snapshot;
the full Forge registry and arbitrary datapack parity remain unfinished. The
source casting-cost prototype computes the minimum registered `item_cost` from
the 43 pinned material-casting recipes. A unit-tested source `MaterialValue`
path now covers `tconstruct:parts`-tagged material-bearing parts: it rejects unknown materials
and zero casting cost, preserves variants, and uses the registered casting cost.
A cost-2 wood variant head yields two cost-1 handles in the source calculation.
The world registry, tags and actual atomic crafting remain unconnected.
The fake-item source calculation checks the distinct compatibility metal and
block tags against visible base-variant material recipes and their float ratios.
Pinned bronze recipes are unit-tested. In both game modes an independent fixture
used test datapacks to override bronze definitions and ingot/block tags, then
checked enable/disable, reload and world isolation. This is a controlled
server-side calculation, not fake-item gameplay. Recipe outputs with NBT or
explicit empty forms, unknown items, custom condition types and
instrument-registry validation fail closed; these are not full Forge loader
semantics. The fake ingot ID is registered with its original GUI model and material naming; command-supplied bronze, silver and unknown variants survived save/reload and their GUI displays were visually checked in both modes. Its crafting/eligibility connection is still absent. The fake storage block and item are registered with the original fallback and material-specific textures. Linux test builds displayed bronze and unknown blocks in both modes, preserved their Material across save/reload and mining, and preserved bronze on in-frame Pick Block. With Mixins cb1ad23, the official Linux build passed host and LAN guest Pick Block in both modes, with and without Ctrl; picking vanilla stone remained unchanged. Normal acquisition remains incomplete; Windows is unverified. Original reference files remain byte-identical in `content/reference/tconstruct-storage-visuals` and can be regenerated with `tools/import_storage_visuals.py`. The independent `raw-entity-probe` fixture stores original-shaped `tconstruct:material_block` / `Material` NBT in an existing unmodelled vanilla block for a controlled persistence test: both execution modes preserved the NBT over save/reload, and only the in-frame host mesh observed it. This does not implement the block or remote synchronization. The server-authoritative `material-block-place.rs` hook implements the material assignment and NBT portion of `MaterialBlock.setPlacedBy` / `MaterialBlockEntity.saveSynced`. `SourceBlockMaterial` also preserves the source distinction between the singleton unknown value and a parsed, equal unknown ID. A separate test-only dirt-template block resource verifies bronze and explicitly parsed unknown NBT after normal placement, save/reload and normal mining in both game modes. `material-block-record-drop.rs` / `material-block-attach-drop.rs` copy the source loot table's Material value onto the dropped fake item. An independent Mixin fixture checks another item's component patch and the fake item's patch in both drop orders, plus untagged position reuse. The test does not establish the original block model, all placement rules, clone, explosion behavior, or actual registration. Conditional native resource preparation registers the original `tconstruct:material_block` entity type when the fake block exists. The `material-block-wire-*` hooks send changed Material values per connection and tracked chunk, clean session state, and apply received NBT to the client chunk. A self-test with an isolated placeholder checked bronze/unknown, no repeated update, host and guest chunk state, guest reconnect, save/reload, and replacement at the same position with an untagged block in both game modes. Remote block-state changes clear the old client-only material NBT without removing server-side loot data. On guest reconnect and world reload, the initial chunk packet contains the Material value without a duplicate follow-up update, as checked in both game modes. The new block renderer has not been verified for every material or resource reload. Server-side loading of malformed or externally edited raw Material NBT has not yet been reconciled with `MaterialBlockEntity.load` and must not be treated as equivalent.

The original `MaterialBlock.getCloneItemStack` copies a usable material even for ordinary pick block. On pinned Horizon, `Game::picked_stack` contains `matches!`; an isolated official Mixins HEAD probe was rejected with `E_UNSUPPORTED_MACRO`. The source `MaterialBlockModel.BakedSingleMaterial` retains the original model for unknown material or missing render information. For other materials it chooses the unique or fallback sprite, color and emissivity before baking. `storage_sprite_by` implements this selection and tests the pinned bronze sprite and fallback cases against the original assets. It is not yet connected to terrain rendering; atlas population, mesh data propagation, lighting and resource-pack reload remain open.

The source mod's 131 fluid tag files are copied byte-for-byte into the source
pack; pinned local Minecraft and Forge jars supply their fluid tags. The game
now collects and resolves these layers against its actual fluid registry. An
independent fixture checked fluid-tag replacement, disable, reload and two-world

the tested resources; original mod fluid registration, source conditions in
gameplay, and cyclic tag ordering remain unfinished.

The 1.20.1 `SimpleJsonResourceReloadListener` puts all successfully parsed
recipe JSON IDs in a Java `HashMap` before Forge filters leading-underscore
metadata. `RecipeManager.getRecipeFor` uses the first match in that map's
iteration order. The unconnected `recipe-order.rs` reproduces normal Java
`HashMap` buckets and resizing, and was compared against a Java oracle for
4,241 IDs from the pinned Minecraft, Forge and TConstruct source packs. Run
`tools/verify_recipe_order.py` with the two pinned jars and a TConstruct clone
to repeat the Java comparison. Java
tree bins are explicitly rejected until ported. It cannot be used as a parity
claim until all of the world's original and additional recipe IDs are loaded,
conditions are evaluated and the lookup is connected to actual transactions.
