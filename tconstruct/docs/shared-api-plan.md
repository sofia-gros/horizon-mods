# Shared API candidates

These candidates are limited to paths used by TConstruct. PlutoLib remains a general library; material definitions, station recipes, tool effects and gameplay rules stay in TConstruct. A candidate is not complete until an independent library demo and a TConstruct use case pass on the same Horizon and Mixins pair.

| Priority | Shared need | Current evidence and proposed contract |
| --- | --- | --- |
| First: item component transport | The new Horizon host already handles custom data, lore and item models; PlutoLib's transport adapter supplies accepted Tool and max-damage components. TConstruct's two older wrapper-cancelling hooks have been removed so the host wrappers and the shared encoder/decoder can run without their duplicate additions. The independent PlutoLib demo passed representative LAN and save/reload checks; the combined TConstruct runtime remains unverified. The shared adapter must preserve item, count, damage and unrelated components, emit each component once and use the host's registry mapping. Arbitrary future patches and unprepared legacy stacks remain outside the proven contract. The shared API must not inspect TConstruct IDs or keys. |
| Next: item behavior | PlutoLib already supplies namespaced handler registration, integer item data, use results and tooltips. Its adapter is verified against an older host, stores only signed integers under `plutolib:data`, and its network hooks need the coexistence check above. TConstruct's Glowing and tool behavior also need world position, permissions, action/actor identity, damage cause, and existing components; the current API does not expose these. Keep those features in TConstruct until a minimal, generic context and authoritative host/guest semantics are designed and tested. |
| Later: registrations and resources | PlutoLib's `Registry::item` and `Registry::block` generate namespaced template declarations. TConstruct already uses template-based declarations, but its resource preparation also assembles source assets, material stats, recipes, tags and overlays; those are not replaceable by the present API. A future shared registration contract should accept validated generic templates and ordinary data components without inventing TConstruct rules or replacing vanilla resources. |
| Later: machine persistence and synchronization | TConstruct currently has custom Station, Chest and fluid transaction/save paths, including ownership, capacity, components and LAN updates. PlutoLib has no generic inventory or workstation API yet. Extract a small reusable storage/transaction contract only around a concrete common use, with atomic validation, component-preserving save/load, and host-authoritative updates; keep slot rules, recipes and material logic in TConstruct. |

The first candidate is largely a host-capability verification, not a request to recreate Horizon's codec in PlutoLib. Existing source inspection alone does not establish that the built-in path covers every TConstruct component or mode. The native host update, Creative integration, and the upstream Mixins diagnostics remain independently unverified.

The TConstruct-side inputs and expected transport contract are in [`tests/fixtures/lan-components`](../tests/fixtures/lan-components/README.md). Their focused check verifies parsing and item NBT save-codec round trips only; the host/guest network round trips belong to the separate generic codec work.

The fixed host's first standard-codec fixture run reported missing per-stack `minecraft:max_damage` and `minecraft:tool`; the retained custom data can hide the loss. The shared library investigation owns the generic fix. TConstruct's [fixture acceptance](../tests/fixtures/lan-components/README.md) records its expected values and guest gameplay checks.

At PlutoLib component-sync prototype `96b7236a6100225d0aa4355b1ffe1b22a36d603e`, the generic bundle modifies `horizon_client_lib::lan::guest::stack_to_network` on return for `max_damage` and `tool`, and `item_sync::from_network` for `tool` decoding. A limited combined plan with the two existing TConstruct transport HEAD hooks and this bundle accepts five injections and one module on Horizon `3a264943c7a3a3ed02e6ee608443f558d98f208f`; it does not type-check or run the combined hooks.

The old TConstruct hooks called the shared encoder and then appended custom data, lore and item model before cancelling their wrapper. Since the current host encoder already writes those components, that could add duplicates; the guest-side HEAD also bypassed `Game::to_network`'s cached-wire-patch branch. The two injections and helpers have now been removed. PlutoLib `41dd894219364f1d5a373a9ec7bb2e2bce047372` independently passed representative LAN, Creative search, save and reconnect checks on Horizon `5197790e5846a82cfc84d9703e37c4c1b75be09c`; its contract covers prepared Tool values, not arbitrary future patches or all legacy data. A limited TConstruct/PlutoLib plan succeeded, but the combined client has not been built or game-tested. Recheck both directions with actual TConstruct-created tools, unknown components and removals, cached patches, save/reload and real LAN before considering this migration complete.

## Tool component normalization boundaries

- Station/Anvil assembly creates `minecraft:tool` in `source-station-world::assemble_with_stats`; `assemble` then applies material effects, upgrades, mining rules and Overslime. Part swaps, upgrades, Crystal changes and Station Overslime operations rebuild through `assemble`. Normalize once after the final `source_overslime::rebuild`, before the result is offered or inputs are consumed.
- Creative variants take a separate route in `resource-tables::enrich_creative_groups`: `assemble_with_stats` → material and upgrade stats → mining → Overslime → SNBT. Use the same finalization after the last mutation and before shared tab/search registration. It cannot be covered just by the Station entry point.
- Repair clones the existing tool and changes damage/broken state; the crafting-table Overslime recipe clones it and changes custom data. These paths do not themselves generate new tool rules. Their precondition must be an already normalized input, including a stack loaded from an older save; they must preserve the real component and other data. Rebuilding the component on every repair or every packet is unnecessary.
- Existing player inventory, containers and item entities are decoded through `horizon_items::item_nbt::item_from_nbt` (also used by `decode_items` and client save helpers). That low-level parser has only NBT, not the connection/world registry needed to validate explicit block IDs. A single universal post-load normalization point with the required registry and coverage of all owning locations has not been identified. Normalizing only Station transactions would leave untouched inventory, chests, drops or Creative-origin items outside the guarantee.

A candidate design is one fallible, idempotent owned-stack finalizer taking the correct block registry: call it at the two producers above, and integrate it once per existing TConstruct stack when it enters an authoritative world/owner context with the registry available, before use, mutation or network exposure. The legacy-load boundary and its ordering still need a concrete supported hook; do not claim it exists. Preserve item/count/damage, all unrelated components and server wire-patch/removal semantics. For invalid or unsupported legacy data, surface a recoverable error and retain the original stack; do not silently drop or fabricate rules, overwrite a future component, consume recipe inputs, or classify old TConstruct stacks as outside scope. If a legacy stack lacks its real Tool component, reconstructing from `tic_mining_tool` requires separate evidence that the saved copy is complete and authoritative; it must not be assumed.

Acceptance needs a previously saved TConstruct tool in player inventory and a container: load with the actual world registry, normalize once, compare canonical stack/search identity and Tool rules, send both directions, use and repair, then save and reload again. Include invalid/unresolved registry references and ensure no inventory loss or false success. This is a proposed integration contract, not a completed migration or a guarantee for arbitrary other mods' saves.

The draft now calls PlutoLib's experimental `prepare_tool` through `source-tool-normalize.rs` after Station/Anvil assembly and existing-stack repair, and before Creative group registration. The block ID map comes from the built-in registry snapshot populated alongside the block-tag snapshot; explicit IDs fail when the map cannot resolve them. A rejected result does not change the stack passed to the finalizer and a rejected Station plan cannot consume inputs. The custom mining mirror is updated to the canonical Tool on success. A stack with a mirror but no real Tool is rejected rather than reconstructed. Before Station repair or rebuilding an existing tool, the original stack's stored patch and snapshot are checked before any damage or component change. Known damage, Tool, max-damage, custom-data, custom/item names, lore, item-model and unbreakable additions are accepted only when their decoded values are available; an already-invalid snapshot, unrecognized or duplicated addition, removal, or malformed patch rejects the plan. A nontrivial normalization of an otherwise valid cached patch is also rejected rather than silently invalidated. This is deliberately narrower than general patch preservation: other legitimate component additions and removals cannot yet be repaired through this path. For a locally opened Station or Anvil, hovering the empty operation result now reports an unsupported patch or Tool validation error. The candidate tooltip has not been game-tested and does not yet carry the authoritative reason to remote guests. These checks do not establish coverage for all legacy save locations or for patches already invalidated before entering the Station.

On Horizon `3a264943c7a3a3ed02e6ee608443f558d98f208f`, a small runner compiled the actual finalizer with PlutoLib commit `a7a3af3fb5ad23db97c3762311eec84d0536e687`: five focused tests passed for representative generated stacks, canonicalization, registry rejection, missing real Tool, original-stack preservation and cached patch behavior. A limited joint Mixins plan accepted one crate, seven modules, seven injections and one state. It is not a build of the transformed client or a LAN/game result. The old TConstruct networking hooks have since been removed; the transport bundle is not yet distributed, and saved tools outside these entry points are not covered.

A focused regression built the actual patch guard and extracted damage/repair-commit helpers with the fixed host codec. It covers an original patch with an unsupported removal that becomes invalid after damage mutation, plus a known-component patch whose synthetic repair plan consumes exactly the planned material. This is not an end-to-end Station recipe, network, save or game test.

The TConstruct Station information panel reads `tic_max_damage` and current damage; the Overslime bar also uses the custom maximum. Its mining-speed and harvest hooks use the `tic_mining_tool` mirror, and conditional effects use `tic_mining_traits` and the custom maximum. These are TConstruct rules and do not prove the host's ordinary advanced tooltip or item renderer uses the real per-stack component. A reusable runtime component reader should expose the host stack's effective max damage and standard Tool rules with item-default fallback; material traits, modifiers, broken-tool behavior and their operation order remain TConstruct-owned. The library team is investigating a generic presentation hook separately.

## Generic mining rule boundary

The reusable runtime contract should evaluate an item's actual standard `minecraft:tool` component when present: ordered rules with explicit block or tag resolution against the active registry: use the first matching rule that supplies a speed, and separately the first matching rule that supplies `correct_for_drops`. Use the component's default speed when no matching rule supplies one. Missing per-stack components must fall back to the host's item definition; ordinary vanilla items and unmatched blocks must retain host behavior. Preserve the standard `damage_per_block` value separately. The same normalized Tool must produce the same result on the authoritative host and the guest's prediction path; a block-destroy event is not a substitute for speed or correct-tool queries.

The current TConstruct `source-mining-return` and `source-harvest-return` read the custom `tic_mining_tool` mirror to override `Items::mining_speed` and `Items::correct_for_drops`. `source-mining-context` and `source-mining-rules::conditional` then apply TConstruct-specific material traits, broken state, upgrade values and potion-dependent ordering. Those effects must remain TConstruct-owned and run once after the generic standard rule result. Replacing the shared rule lookup must not erase the existing material rules, silently use an invalid mirror, or imply that the 519 host has been game-tested.

TConstruct currently selects effective speed and harvestability from its generated mining rules, rejects broken tools, and applies material traits after the host speed calculation. The shared evaluator must read the actual Tool component; preserve TConstruct's tier policy and trait ordering around that evaluation. The representative [mining-order fixture](../tests/fixtures/mining-order/) records a tier mismatch and an additive-then-multiplicative trait case. Migration awaits the library API and runtime verification.

The experimental PlutoLib Tool rules candidate `073a57ce74bb006f72ce4c8709d7e588d4bf4ab6` evaluates the actual Tool component through its public parser. TConstruct retains its tier-denial, broken-tool and material-trait policies around that evaluator. A limited joint transform and Horizon items crate tests cover representative rules; the combined client and real game remain unverified. The bundle must be installed alongside TConstruct at the same Horizon revision.

Station and Anvil diagnostics now originate in the host's preview plan and travel with its existing menu data frame. Unsupported saved component patches and Tool preparation failures leave inputs untouched. The guest displays the host reason for an empty result, and a later preview replaces or clears it; closing a station clears the local menu data. The frame and isolated injection plans have lightweight checks only; combined client compilation and real LAN remain unverified.

Saved item stacks are decoded by `horizon_items::item_nbt::item_from_nbt`, used by player inventories, block-entity inventories and item entities. That common decoder has no block registry. The TConstruct registry snapshot is populated later during recipe reload; chunks and entities may also load after that event. A single safe post-load boundary covering all owners has not been established. Existing saves therefore remain unchanged until a registry-aware, non-destructive boundary is verified; failed Tool preparation retains the original stack.

For modifier application, overslime refill, part replacement and Worktable extraction, the original stack is checked before a clone is changed; assembly does not recheck the changed clone. Repair keeps its own pre-mutation check and new tools have no original stack. Focused cached-patch tests cover the shared guard and commit helper; full recipe execution still requires combined runtime verification.

The item-use API must provide the acting player and hand/stack, authoritative or predictive side, interaction kind, target block and face, and access to the existing world and permission checks. Glowing checks both clicked and candidate positions, replaces only permitted space, and charges durability only for a successful placement. Attack input also needs start, held and release semantics: a long press must not fire the action repeatedly. The handler must distinguish pass-through, handled success and cancellation without suppressing unrelated vanilla interactions. Tooltips need the actual stack and existing text/color output; TConstruct retains its own descriptions and material rules. Projectile hits and equipment movement use separate events and are not implied by item use.

The cached-patch fixture now calls the real modifier and Crystal extraction recipe planners, plus the real Overslime refill calculation, with a known patch; it also checks rejection of an unknown patch without consuming the fixture inputs. It does not run `operation_plan_diagnostic` or `extraction_plan`: those require the host World, generated ChunkMap state and populated recipe, material, tag, durability and block-registry snapshots. Full assembled-output behavior remains unverified by this fixture.
