# Scoped Step 2 follow-up: no new API selected

This is a bounded source investigation following the 51-PR delta ledger, not a declaration that all PlutoLib commonization is complete. No runtime source, PR state, Actions configuration or native job changed. The discarded Horizon fork was not accessed. Exact source identities are in `remaining-candidates.json`.

## Candidate decisions

1. **Indexed menu words:** five actual branches in `part-selection-remote-data.rs` append a word only when its index equals the pending vector length; otherwise they discard that key's pending vector. They use three caller-owned maps. Begin/abort/finish, actor/container routing and committed display handling differ by stream: a station reason has three fields, builder info seven, layouts validate pairs, cast costs parse a separate schema, and pattern failure clears choices. A tiny public append helper would not solve these lifecycle differences. The existing menu-word codec already validates complete frame length/UTF-8. An early word-count cap would be a behavior change, not a faithful extraction. No new API or cap was introduced.

2. **Recipe/index/preview repetition:** the actual fake-material and Travelers UI invalidators are identical, but S06 already owns that mechanic. S07 current-value index CAS, S08 explicit preview and S09 deny-only placement cover the generic services. Remaining family IDs, material selection, display allocation and publication sequencing are consumer policy or the existing unresolved lifetime/authority boundaries. A second registry/cache/preview API would duplicate shared ownership.

3. **Effective stack size:** the products adapter intentionally follows official Menu's valid per-stack `minecraft:max_stack_size`, removal and fallback behavior. The reviewed shared storage planners accept caller-supplied limits; they do not duplicate that calculation. Smeltery guest code deliberately uses a catalog limit. Replacing it with per-stack limits merely to create a common caller would change consumer policy. No new effective-limit API was added.

4. **Changed-or-expired refresh:** broad and Haste snapshots repeat a small timer/byte comparison, but the real actor/reload/invalidation ownership remains outside that calculation. This remains a source-only deferred candidate, not a new transport service or an outstanding promise to implement it.
