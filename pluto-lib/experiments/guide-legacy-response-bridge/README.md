## Narrow capability and registration

The internal registry cannot reuse observer SUBSCRIPTIONS: that public callback is fn(Payload), without native state or mutation capability. Extending it with Game would invert the host-independent crate dependency and silently widen a read-only contract. The proposed separate registry is Game-private; it stores only static descriptors, selector strings, byte ceilings and function pointers. It stores no Game/Packet references and exports nothing through the authoring facade.

The sole mutable capability is a borrowed non-lectern View: read its existing native pages, or make one nonempty replacement with the old cover/clamp/assignment statement order. It cannot open, close, turn input, switch actor/world or access Game. The read-only context getter is same-crate trusted glue and supplies the consumer sequence from the current Game, after callbacks. This is not ownership of a retained opening, protocol sender or screen.

Same static descriptor registration is idempotent; a different descriptor with the same ID or channel rejects, with a visible native system message and error log before an open/request. The registration result is frozen in OnceLock because no unregister exists; the failure log and system message are limited to one per process, claimed before notification for reentry. A poisoned updater registry emits only a once-per-process log after still performing read-only observation; it never adds a popup for an unrelated custom channel. No silent legacy fallback, hidden send or disabled listener is introduced. No unregister is provided in this limited startup/on-use bridge. Registry locks protect only static entries; no consumer function runs under them.

The updater is selected before the existing read-only observer. Afterwards context is recomputed and the current non-lectern View is borrowed. A callback can register for future packets but cannot alter this call's selection. The exclusive borrow prevents safe re-entry into Game while updating; no raw Game reaches the updater. Other native/observer callbacks may have changed Game before the context/view acquisition, so the updated current value is used. The snapshot is non-Clone and consumed once, but a later same-sequence packet receives a new call and remains eligible, matching the old behavior.

## Explicit compatibility differences and pending gates

The old HEAD skipped native packet observation. This bridge intentionally restores native observer -> Pluto read-only observer -> legacy update ordering. Native handle_packet then resumes. Its full body is byte-identical between f4dc and41f; the TConstruct channel is not any of the four reserved CustomPayload arms. Its final wildcard must be pinned as a no-op in the source/oracle gate. If a native observer changes current sequence/pages, the callback uses those current values instead of stale pre-observation facts. A panic before update produces no update; a panic after attempted assignment is outcome-unknown, never an automatic retry.

Old wire accepts repeated same-sequence replies and refreshes retained books beneath overlays. Both stay. 262144-byte body plus8 header is admitted by this updater's explicit262152 ceiling even when the read-only observer skips notification. Empty/malformed/wrong sequence/wrong book/non-view/lectern input must leave old state unchanged. The existing close/reopen wrapping-sequence weakness remains; no lifetime completion is claimed. Language refresh, source-anchor remap, display-title identity replacement and negotiated localized protocol remain separate.

Required before activation: exact module privacy/type/registration call proof on41f; full package plan/exclusive observer guard; native ordinary CustomPayload callback ordering and body no-op oracle; old/new actual Text wire/output and boundary cases (including repeats, overlays, cover, clamp/history); registry conflict/idempotence/reentry and failure reporting; complete unified-package type gate. Actual Client/UI/LAN execution remains a distinct later requirement. The new41f transparent-background drawing hook also needs its own consumer-preserving adjustment; this response bridge does not change drawing.
