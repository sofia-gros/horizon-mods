# Stored crafting policy bootstrap, excluded candidate

Base `24b8ff1671db1ed2fb3c0d0a9c0c952f6f0211fc`, official Horizon `41f822b659789780f58d32c63ddfb6887ea1b8bf`, Mixins `5a64af938ec86b00d53d16a408aabc0038fb3e57`. This adds no ordinary module, hook, state or workflow. Both old denial hooks, Overslime hooks and placement behavior remain installed exactly as before. The stored-policy source group is frozen independently and is not modified here.

## Candidate startup contract

Two noncancellable HEADs at `Recipes::empty` and `Recipes::from_sources` call one private bootstrap module, one `OnceLock<Result<(), RegistrationError>>`, and the same single `register()` function in the excluded consumer. The registry itself remains the existing Pluto matching registry. No actor/global recipe map/TLS, additional registry or per-world identity is introduced. The fragment is a proposed TConstruct manifest addition, not a standalone bundle or a validated/installed hook.

Success publishes one registration before either native constructor body runs. Repeated loads and concurrent constructor calls reuse the cached result. The initializer only validates a static ID and inserts one static interest/callback pair under the existing registry lock. It does not execute those callbacks, enter Recipes, load resources or call external code. Recursive initialization is not supported: a same-thread recursive `OnceLock` initializer could deadlock. Source and complete-plan checks must preserve the stated non-reentrant call graph and exclude competing constructor hooks.

A normal registration error is cached **before panic**. `empty()` returns `Self`, so it cannot express a recoverable `Result::Err`; returning an empty table or silently proceeding would lose the policy. Both constructors therefore use a deliberate fatal initialization failure for DuplicateId/EmptyId. This is not a graceful load error. Depending on the native panic policy/caller, it unwinds the current thread or aborts the process. A caller that catches the panic still cannot construct a new table through these constructors: the cached error panics again. Existing registry entries are not overwritten; single-entry registration rejects normal errors before insertion. If an unexpected initializer panic occurs before the result is cached, standard `OnceLock` permits a retry. This does not promise rollback of arbitrary allocator failures or side effects. There is no unregister, reset or success-to-error transition.

The guarantee proposed is **no new Recipes value returned from a failed guarded constructor**, not global transaction rollback. Native resource reads and caller operations before constructor entry remain outside it. In particular, `remote_recipe_content` takes its pending incoming list before calling `from_sources`; a first-initialization panic does not restore that list. Its `synced = Some(recipes)` publication and cache invalidation occur only on `Ok`, after successful construction. If earlier startup completed successfully, later remote reloads see the same cached success rather than re-registering. No new table is partially published by the candidate, but installation cannot yet be called safe for every lifecycle until applied constructor and actual caller checks pass.

## Owning type and callers

`audit.json` pins the entire official crafting.rs and exact type/constructor bodies. The owning file has one `impl Recipes`, two construction literals (`empty`, `from_sources`), private facts/curses/cook_index fields, no derived/default/clone constructor, and only its cfg(test) child module. `load` reads sources then delegates to `from_sources`. Aliases of the same type still call the same methods. Returning/transferring an existing object is not a fresh unguarded construction; later mutation of public crafting vectors is covered only if that initial object passed the startup boundary.

The remote runtime directly calls `horizon_client::crafting::Recipes::from_sources`, so `Recipes::load` or Game resource loading alone cannot be the bootstrap. The `Recipes` literal in the same native_recipes file names the separate `NativeRecipes` alias, not this type. `StationRecipes` is also a different type. Exact symbol searches found `Recipes::empty` in menu tests, and from_sources in native remote handling and recipe-book tests; these call sites supplement, not replace, the owning-type proof. Future/generated private child modules, constructor/state transforms, unsafe synthesis and complete mod composition remain unproved. A complete plan must reject new unreviewed sources that could create or publish this type outside the pinned constructors.

## Required gates before replacing old hooks

1. Run the **full real API unit inventory**, separately identify the six new matching tests, and run all sixteen unchanged finite-policy fixture tests. These test native stored values/old policy equivalence, not installed startup.
2. Run the five source-prepared bootstrap helper tests with the actual API error type. Their local locks and simulated registration/body counters establish only helper behavior. They do not synthesize a fake Game or claim native constructor execution.
3. Actual official plan must accept both no-binding noncancellable constructor HEADs and both candidate modules. Pin the exact source fingerprints, target/owner/id/priority/void behavior and the complete set of injected modules/hooks/states. Both constructor targets must be exclusive to the proposed startup hooks; otherwise a prior cancellation could bypass them or another constructor callback could reenter initialization. No exception is added to the existing `assemble_if_matches` exclusive guard.
4. Applied type/startup tests must verify actual hook placement before both native bodies, real single registration on empty/from_sources/load/direct remote construction, repeated and concurrent loads, actual duplicate rejection before object publication, and no second API crate or registry instance. Panic handling and unsupported call paths must remain explicit.
5. Only a separately reviewed full composition may remove the two old denial hooks after equivalent registration exists. Overslime output/remainders and placement transaction have separate authority and are not converted to veto or removed to pass guards.

## Existing fact meaning retained

`TemplateFacts.has_components` currently means `Template.extra.is_some()`, the old normalized projection. It is **not** the presence of every 41f raw `Template.components` patch. Explicit damage zero and removal markers may be absent from that flag. This group deliberately retains the old field meaning and literals. These two policies use the stored native `Template::create()` result, matching their old helpers, not raw parse/over patch semantics. A future consumer that actually needs raw patch presence or contents requires an explicitly distinct field/capability; silently redefining this boolean is not part of this migration.

No Rust, metadata, plan, apply, host type or gameplay test was executed for this bootstrap group. Source/Python validation and native proof are separate.
