# Part Builder on PlutoLib: what is done and what is missing

Status as of 2026-11-07, Horizon `ebcfa226` / Mixins `5a64af93`.

## Phase 3 vertical slice (done, locally verified)

Wood and flint pickaxe, using **only** data recipes and the mod's registered items; no TConstruct
injection into the host remains in the slice (`tools/smoke-local/slice.json` keeps only
`prepare-station-resources`, the content loader):

| Step | Recipe (`tconstruct/content/data/tconstruct/recipe/`) |
|---|---|
| Pick head | `flint_pick_head.json`: 1 flint (shapeless) |
| Handle | `wood_handle.json`: 2 sticks, vertical |
| Binding | `wood_binding.json`: 2 sticks, horizontal |
| Tool | `flint_pickaxe.json`: head + binding + handle (shapeless) |

`tools/smoke-local/smoke.py` crafts this chain in survival mode through the real inventory crafting grid
and asserts one `tconstruct:flint_pickaxe` and no leftover parts.

This replaces the Codex prototype `command.rs` (`/tconstruct parts|assemble`), which mutated
`game.inventory` directly. The prototype stays in the full manifest (parked) because Rust and Python tests
still reference it.

## What this is NOT

- It is not a Part Builder block or screen. The pickaxe is still the template item generated by
  `tconstruct/tools/resources.py` (stone pickaxe behaviour), not a material-driven Tinkers tool with
  stats, traits and modifiers.
- Mining speed/durability from materials is not covered.

## Missing PlutoLib capability (blocker for a real Part Builder)

PlutoLib today offers registration, Creative tabs, Tool-rule evaluation, tool codec/transport,
inventory/storage, fluids, component display and several guarded host seams. It has **no** API for a
station: a block-opened container menu with custom slots, click handling, rendering and LAN sync.
The existing Part Builder implements that with ~60 injections into Horizon UI internals
(`menu_click`, `draw_chest_screen`, `lan_station_button`, ...), which breaks the "PlutoLib only" rule
and is exactly the kind of hook upstream rejects when it refactors.

Needed, in order, each as its own PlutoLib PR with its own guard and smoke test:
1. A station-menu service (open, slot layout, click/drag policy, close, spill) with explicit LAN ownership.
2. A station-screen drawing seam (slot backgrounds, selection list, tooltips).
3. A tool-build transaction API (parts + material stats -> Tool component) on top of the existing tool codec.

Until then TConstruct keeps tool crafting on data recipes; the Part Builder returns as consumer code
once those PlutoLib APIs exist.
