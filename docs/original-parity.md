# Original parity tracking

The specification is the complete Tinkers' Construct 1.20.1 tree at
`f4e77d43f39ba1047bf93ae816b7e1beaab514c2`, including behavior, appearance,
content, data, input, rendering, audio, persistence and multiplayer. An internal
implementation may differ where its observable behavior is equivalent; the
prototype's user-visible differences below are gaps, not alternative targets.

[upstream-tree.txt.gz](upstream-tree.txt.gz) indexes all tracked upstream
paths, regenerated by `python3 tools/upstream_inventory.py /path/to/clone`.
The file inventory is an audit aid, **not** an assertion that each file has
been analyzed or mapped to a feature. The coverage matrix is incomplete until
registrations, data-driven combinations, lifecycle paths and their tests are
mapped. [Feature matrix](feature-matrix.md) and [roadmap](roadmap.md) identify
known gaps; missing entries must not be interpreted as implemented.

[upstream-recipes.json.gz](upstream-recipes.json.gz) contains the original
JSON and source path for all 338 generated material recipes, 28 Part Builder
recipes and 23 station layouts; regenerate it with
`python3 tools/reference_catalog.py /path/to/clone`. Every catalog entry is
currently marked `unreviewed`: the prototype coverage in the table below is
partial and does not establish parity for an entire recipe. These are file counts,
not verified counts of active features; conditions, aliases and runtime
registrations still have to be audited. The current three fixed choices do not
cover those definitions. The material directory includes 217 material-input
recipes, 73 fluid material recipes and 48 material-melting recipes; the part
builder directory contains 24 material-part and four item-part recipes. This
counts source `type` fields, not enabled recipes. Conditions, leftovers and
nontrivial ingredient forms require implementation, not conversion to fixed
item matches.

## Selection-state implementation probe

`tests/fixtures/selection-state/` is an isolated experiment, not a production
feature. The pinned Mixins CLI applied a state field to the official Horizon
`ChunkMap` and the resulting `horizon-client` library passed a locked offline
Cargo check. It is scoped to each chunk map, avoiding a process-global registry.
The production code now uses world-scoped selection and has hooks to remove it
on block change or chunk unload; block replacement was tested, chunk unload was
not exercised. Fixed-part button selection, preview and result pickup
were exercised in both game modes and under two-player contention. Original
recipe-derived selection and full lifecycle parity still require implementation
and tests.
The original `PartBuilderBlockEntity` recipe-selection and refresh paths are
the acceptance reference; do not encode the selection as a real droppable item.

### Repair calculation investigation

At the pinned revision, `MaterialStatsModule.addTraits` adds traits from each
part and `ModifierEntry.merge` adds levels. The default wood trait data names
Cultivated with `each_level: 0.5`; `RepairModule` applies its percent formula.
For the original flint-head/wood-handle/wood-binding combination, this implies
Cultivated level 2 under the normal trait path. Flint head repair uses durability
85, and `MaterialRecipe.scaleRepair` divides by `INGOTS_PER_REPAIR = 3` before
modifier factors. `TinkerStationRepairRecipe.repairFromSlot` uses `ceil` for
items needed and truncates the total per input slot to an integer. Under those
assumptions one flint repairs 56 and two in one stack repair 113 before capping
at the tool's damage. The current fixed `56` per item does not represent the
fractional calculation or configurable trait behavior. Original runtime
comparison, alternate trait configuration, rounding boundaries and all other
materials remain unverified; do not generalize the prototype's tests.
